## A. 功能项（按必要性排序）

### A1. 部分解压：只解压选中的条目 ★ 最必要的功能缺口
- **现状（2026-10-26 已实现）**：解压视图条目表带选择列与三态目录行；默认全选时
  不传 `entries`、仍走整包路径；显式选择只下发选中文件与完整选中的最上层目录，
  半选父目录不会被下发（否则会覆盖子项取消意图）。`/api/extract` 的
  `entries: [path,...]` 保留"显式目录=整棵子树"契约，并剪除被祖先覆盖的冗余后代。
  7z / ZIP / 分卷走 7zz 真实条目参数，zipfix 路径按解码名过滤；`tar.zst` 明确禁用。
- **回滚（2026-10-26 返修）**：fresh 目标失败/取消整体删除；merge 目标先做文件清单
  快照，只清本次新增文件与新建空目录，既有文件与其他任务产物保留。被 overwrite
  覆盖的旧内容不保证恢复（未实现备份）。
- **依据**：这是「解压缩工具」的及格线功能，The Unarchiver / Keka 都有；
  大包里只想要一个文件时现在只能全解压再删。

### A2. 向已有归档追加/删除文件
- **现状（2026-10-27 仍未做）**：`engine.py:502` 只有 `a`（新建），无 `u`/`d` 调用；归档一旦创建
  只能重建。
- **方案**：在解压视图加「修改」模式：拖入文件 → `7zz u`；选中条目删除 →
  `7zz d`。限 7z/zip（tar.zst/rar 不支持修改，UI 直接禁用并说明）。
- **依据**：压缩包里补一个文件是高频操作，重建大 7z 要全量重算。
- **注意**：zipfix 修正名的 zip 禁止原地修改（编码映射与中央目录不同步），
  提示用户先解压重组。

### A3. 签名与公证（上轮 C6，人工项）
- **现状**：`codesign -dv` 无 TeamIdentifier，DMG/pkg 均裸包。
- **方案**：Apple 开发者证书 → codesign（hardened runtime + entitlements 最小集）
  → notarytool → staple；package.py 增加签名/公证步骤。
- **依据**：不分发则已，一旦分发，Gatekeeper 拦截会让"成品"无法到达用户。
  这是从"自用工具"到"可发布产品"的唯一硬性门槛。
- **前置依赖（第五轮验收结论，2026-10-23）**：**D2 的 Touch ID 密码保护在签名前不可用**。
  钥匙串 ACL 条目（`kSecAccessControlUserPresence`）写入需要 `keychain-access-groups`
  entitlement，未签名构建实测 `SecItemAdd` 返回 `-34018`（errSecMissingEntitlement，
  对照实验：无 ACL 写入正常）。A3 完成后必须补一次真人端到端验收：
  开启 touchid → 存密码 → 重启 → 解压触发系统认证框 → 通过后自动解锁。
- **另需在 A3 轮处理**：A4 的 `verify_signature()` 槽位接入 codesign 校验
  （appupdate.py:115）；`bundle.py` 的签名步骤；A4 错误返回卫生问题
  （非法仓库格式 500 + 类名前缀 → 400 + 干净文案）。

### A4. App 自身自动更新
- **现状（2026-10-27 已实现，轻量方案）**：`src/arca/appupdate.py` 走 GitHub Releases：
  检查 → 中文说明 → 手动确认 → SHA256 与 sidecar 逐字比对 → 下载替换应用包（旧包留作
  恢复）→ 外部脚本等进程退出后重启，新版启动失败保留旧包并提示人工恢复路径。错误返回
  已治理（`UpdateError` → 400 + 干净文案，仓库格式解析错误 → 400，不再 500 + 类名前缀）。
  `verify_signature()` 仍是占位槽（appupdate.py:117），待 A3 签名后接入 codesign 校验。
  套件：appupdate 29 项。
- **依据**：引擎更新管线已全套现成（摘要解析、流式校验、进度、回滚），
  边际成本主要在发布流程而非代码。

### A5. 创建格式补 tar.gz
- **现状**：`CREATE_FORMATS = ("zip", "7z", "rar", "tar.zst")`（engine.py:32）。
- **方案**：7zz 支持 `-tgzip`，一行格式注册 + UI 选项即可。
- **依据**：与 Linux/服务端交换时 tar.gz 仍是默认要求；现在只能用 tar.zst，
  对方机器多半没有 zstd。

### A6. 加密包密码的 Keychain 托管
- **现状（2026-10-27 已实现）**：Keychain 托管已落地（keyring 套件 53 项断言）：默认
  关闭、设置里可开；解压加密包可勾选「记住此密码」，按包记忆，下次自动填充。Touch ID
  保护走 `kSecAccessControlUserPresence`（keyring 套件含 mock 断言），但未签名构建写入
  ACL 实测返回 `-34018`（见 A3 前置依赖），签名后必须补真人端到端验收。
- **依据**：反复处理同一批加密包的用户刚需；macOS 上有系统级安全容器，
  比竞品（Keka 存明文偏好）更安全。
- **边界**：只允许用户主动勾选才写 Keychain，绝不静默记忆。

## B. 性能项

### B1. 任务队列保守并行（上轮 C5 的正式版）
- **现状（2026-10-27 已实现）**：双 worker 任务队列（`src/arca/jobs.py`）；任务按输出
  目录分桶（`bucket`），同桶串行、异桶并行，zipfix/7zz 调用不变，只动调度。
  concurrency 套件 4 项锁定行为。
- **方案原文**：worker 池 2；任务按输出目录分桶，同桶串行、异桶并行；
  UI 的 `nav-count` 已支持多 active。zipfix/7zz 都不动，只动调度。
- **依据**：用户拖 3 个包同时解压是常态；实测排队等待是纯等待，IO 与 CPU
  都有富余。上轮的担忧（同目录并发写）用分桶规则规避。

### B2. 压缩进度细化
- **现状（2026-10-27 已实现）**：扫描阶段任务卡副标题实时显示「已扫描 N 个文件 ·
  约 X GB」（复用 C2 的空间预检统计）；7zz 输出里的 `Scan` 行也映射为「正在扫描」
  阶段，进度条不再停在「准备中」直到 1% 才动。
- **方案原文**：扫描阶段在任务卡副标题实时显示「已扫描 N 个文件 / 约 X GB」
  （C2 的空间预检已把这个统计做成了现成的——直接复用给 UI）。
- **依据**：大目录压缩头 30 秒"死机感"是当前最明显的性能体验问题，
  不是慢，是看不见它在干活。

### B3. inspect 冷启动加速
- **现状（2026-10-27 已实现）**：ZIP（含 UTF-8 包）一律先用 Python zipfile 读中央目录
  （`engine._inspect_zip`），7zz 仅作回退（加密、分卷、不支持的压缩方法、结构异常）；
  7z/rar 维持 7zz。A1 的成员校验（`engine.list_entries`）也走同一条无 800 条上限的
  纯 Python 路径。
- **方案原文**：zip 文件一律先用 Python zipfile 读中央目录（含 UTF-8 包），
  7zz 仅作回退（损坏/加密条目），预期列表显示提速 5-10 倍；
  7z/rar 维持 7zz（无内存解析器，不值得引入依赖）。
- **依据**：zip 是最高频格式；zipfix 已验证了纯 Python 路径的可靠性，
  本质是「把 F1 的特殊路径升级为主路径」。

### B4. 大列表渲染上限
- **现状（2026-10-27：按判定保留，未做虚拟滚动）**：已实现「首屏 200 条 + 主动展开
  最多 800 条」（`#x-show-all`）；**没有**虚拟滚动或分页。真实 headless Chrome 实测
  展开 800 行 111.7 ms，低于 300 ms 交互预算，判定与后续触发条件见
  [`docs/BENCHMARK.md`](BENCHMARK.md)（`scripts/benchmark_ui.py`）。
- **方案原文**：条目表改虚拟滚动或「显示前 200 条 + 加载更多」按钮。
- **依据**：800 条 innerHTML 一次性渲染在慢机上会卡帧；配合 A1 勾选后
  这个问题会被放大，宜提前做。

## C. 工程项（支撑 A/B 落地）

### C1. CI 化
- **现状（2026-10-27 已落地，本地版）**：`scripts/all_test.py` 已收拢为 26 套件的
  一条命令全量门禁（含 headless 实例编排与隔离 HOME）；`make verify` / `make test-fast`
  提供快速预检。仍无远端 CI——本仓库没有 CI 运行记录，`make test` 是唯一完整可信信号。
- 两轮执行都靠人工贴命令 + 对方手工跑门禁。把 `node --check` /
  design_audit / menu_test / integrity_test / selftest / 三个新单测收成
  一个 `scripts/all_test.py`（或 CI workflow），验收方才不用再逐条复跑。

### C2. 测试的跨度依赖与外网依赖
- **现状（2026-10-27 已修复）**：`update_test.py` 的清单断言改为「行数 == 实际跨度」
  （长清单滚动在跨度不足时明确 skip，不再恒失败）；RAR 样本已本地 vendor 化
  （`tests/fixtures/seektest.rar`，SHA256 校验，下载仅作兜底），selftest 的 RAR 读取
  不再依赖外网（39/0/0，无跳过）。
- `update_test.py` 的「≥13 行」「跨越 N 个版本」断言对 26.04→26.05 单版本
  跨度恒失败（第二轮验收已踩到）；`selftest.py` 的 RAR 样本依赖外网下载
  （本轮两次失败）。方案：版本清单断言改为「行数 == 实际跨度」并单独构造
  合成历史数据测滚动；RAR 样本本地 vendor 化（几 KB 即可）。

### C3. 行为探针入库
- **现状（2026-10-27 已转正）**：`scripts/acceptance_probe.py` 已入库，作为
  all_test 的 acceptance 套件（22 项）。
- 两轮验收各写了一份探针（`build/accept_probe.py`、`build/accept2_probe.py`），
  覆盖 GBK/空包/409/只读/空间预检/缓存失效。建议转正为
  `scripts/acceptance_probe.py`，成为以后每次交接的标准验收工具。
