# 性能基准与 B4 判定（2026-10-26，2026-10-27 补 full 与长时 soak）

> 本文件只记录**实际跑过**的数据。没有同条件前后对比，因此不宣称任何性能提升。
> 原始 JSON 写入仓库 `build/`（`build/benchmark-*.json` / `build/benchmark-ui-*.json` /
> `build/soak-*.json`）。2026-10-26 那次外部磁盘脱机期间的历史归档保留在
> `.tmp/p1p3-logs/`；2026-10-27 返修已在原仓库 `build/` 正常复跑，下方 UI 数据即
> 本轮实际结果；2026-10-27 另补跑了 full 档与 30 分钟以上长时 soak。

## 怎么复现

```bash
build/venv/bin/python -S -E -B scripts/benchmark.py --mode quick
build/venv/bin/python -S -E -B scripts/benchmark.py --mode full
build/venv/bin/python -S -E -B scripts/benchmark_ui.py
```

- `quick`：1000 条 ZIP inspect、64 MiB 随机文件 7z 压缩+解压、2000 文件/200 目录扫描、4 路并发 inspect。
- `full`：同样的用例，512 MiB / 20000 文件 / 1000 目录 / 8 路并发。**不是** 1 GB 或 10 万文件的测试。
- 语料全部由固定脚本生成在 `build/`（`build/bench-*`、`build/bench-ui-*`，Chrome profile 在 `build/chrome-bench-*`；UI 基准的 HOME 用系统临时目录），跑完自动删除；不读取用户文件。
- 磁盘不足时脚本明确输出 `SKIPPED` 并退出 0，不会编造数字。
- 峰值内存取 `resource.getrusage(RUSAGE_SELF).ru_maxrss`（macOS 单位为字节），CPU 取 `time.process_time()`。

## 基线（本机，2026-10-26）

- 机器：macOS 27.0.1 / arm64 / 10 CPU / 16 GB / Python 3.13.12
- 引擎：内置 7-Zip 26.05

### quick（`.tmp/p1p3-logs/benchmark-quick-final.json`）

| 用例 | 样本 | 耗时 | CPU | 峰值内存 |
| --- | --- | --- | --- | --- |
| ZIP inspect | 1000 条（返回 800 条，JSON 132,523 B，截断 200） | 0.005 s | 0.005 s | 33.0 MB |
| 7z 压缩 | 64 MiB 随机数据，`-mx1` | 1.921 s（产物 67,113,211 B，接近不可压） | 0.002 s | 100.3 MB |
| 7z 解压 | 64 MiB | 0.142 s | 0.003 s | 100.3 MB |
| 扫描 | 2000 文件 / 200 目录 / 128,000 B | 0.020 s | 0.017 s | 100.3 MB |
| 并发 inspect | 4 × 1000 条 ZIP | 串行 0.027 s / 并行 0.029 s（speedup 0.93） | — | — |

同条件重复跑（2026-10-26 17:06 与 17:22）的耗时在 0.005–0.012 s（inspect）、
1.9–3.3 s（64 MiB 压缩）之间波动，属于页缓存与机器负载差异；本轮只报告测量值，
不宣称任何"变快/变慢"。

注：压缩解的 CPU 时间远小于墙钟时间，说明 7zz 子进程的 CPU 没有计入本进程
`process_time`，这是预期行为；不要把它读成"压缩不耗 CPU"。

**并发结论**：4 个 1000 条 ZIP inspect 的串行与 4 线程几乎相同（0.93×）。这些小
归档的 inspect 是毫秒级 CPU/IO 混合任务，线程池收益被调度开销抵消；这次数据**不**
支持"并发 inspect 更快"的结论，也不作为 B1 并行任务队列的证据（那需要真实压缩/解压
任务与不同输出目录，未在本轮范围内）。

### full（本机，2026-10-27 实跑）

full 与 quick 是**不同数据规模**：两档数字不能直接读成"变快/变慢"。本轮只建立 full
基线，不宣称任何优化或回退。

- 命令：`build/venv/bin/python -S -E -B scripts/benchmark.py --mode full`
- 原始 JSON：`build/benchmark-full-20261027-045755.json`
- 完整日志：`build/benchmark-full-20261027-045755.log`
- 环境记录：`build/bench-env-full-20261027-045755.txt`
- 墙钟：2026-10-27 04:57:55 → 04:58:58（`/usr/bin/time` real 63.20 s，含语料生成与清理）
- 机器：macOS 27.0.1 / arm64（Apple T8132）/ 10 CPU / 16 GB / Python 3.13.12；
  内置 7-Zip 26.05；`build/`（外置 SSD）运行前后可用 252 GiB（脚本估算需 ~2.5 GB，
  未替换 build symlink，未迁移仓库）；运行前 load average ≈ 5.7（系统常驻负载，未清场）
- 数据规模（JSON `parameters` 实际值）：512 MiB、20,000 文件、1,000 目录、8 路并发
  inspect；JSON 无 `skipped` 字段，确认真实执行而非磁盘不足跳过

| 用例 | 样本 | 墙钟 | CPU（本进程） | 峰值内存 |
| --- | --- | --- | --- | --- |
| ZIP inspect | 1,000 条（返回 800，JSON 132,567 B，截断 200） | 0.0048 s | 0.0041 s | 30,146,560 B |
| 7z 压缩 | 512 MiB 随机数据，`-mx1` | 11.7453 s（产物 536,904,827 B，接近不可压） | 0.0024 s | 567,246,848 B |
| 7z 解压 | 512 MiB | 0.7466 s（输出 536,870,912 B，大小一致） | 0.0015 s | 567,246,848 B |
| 扫描 | 20,000 文件 / 1,000 目录 / 1,280,000 B | 0.2467 s | 0.1272 s | 567,246,848 B |
| 并发 inspect | 8 × 1,000 条 ZIP | 串行 0.0369 s / 并行 0.0434 s（speedup 0.85） | — | — |

口径与读法：

- 峰值内存是整个基准进程的 `ru_maxrss`，被"生成 512 MiB 随机缓冲"抬到约 541 MiB，
  **不是**应用解压 512 MiB 时的常驻内存；不要把它当应用内存基线。
- 压缩的 CPU 时间远小于墙钟，因为 7zz 子进程的 CPU 不计入本进程 `process_time`；
  不能读成"压缩不耗 CPU"（同 quick 段的说明）。
- 8 路并发 inspect 在本机没有收益（0.85×），与 quick 的 4 路（0.93×）方向一致：
  小归档 inspect 是毫秒级 CPU/IO 混合任务，线程池调度开销抵消收益。本轮不做并发优化。
- 测量期间未同时运行其他测试或 soak。

- 轮数：**512**；失败：**0**；未终结任务：0；心跳：64 次（每 30 s）

| 场景 | 512 轮累计 |
| --- | --- |

| 部分解压（只选 1 项，校验未选项不落盘） | 512 |

| 损坏 / 截断 / 垃圾 ZIP（4 变体）+ 路径穿越归档 | 2,560 次解压 + 2,048 次 inspect |
| 错误密码 + 正确密码 | 512 / 512 |
| 受控低磁盘（mock disk_usage，不写满真实磁盘） | 512 |
| 任务记录清理 | 每 20 轮 `clear_finished`，共 25 次；只清完成态，中断记录未出现 |
| journal / 临时文件清理 | 每轮断言 pending=0、本轮目录已删；最大临时树 34,015 B / 2 文件 |

监控趋势（64 个心跳采样点，30 s 间隔）：

- **RSS**：35.4–57.7 MB，峰值 60.9 MB，末次 41.4 MB；无随轮数单调增长的趋势。
- **文件描述符**：全程 6，无增长。
- **子进程**：心跳采样时 0；结束 drain 后 0（引擎子进程在单轮任务内启动并被回收，
  取消路径也会 terminate/wait）。心跳只能证明"没有跨轮累积"，不能排除任务运行瞬间的
  短暂子进程。
- **临时树 / HOME 状态**：全程 2 个文件 / 约 34 KB；`pending-jobs` journal 恒为 0，
  没有出现无界增长。
- **任务记录**：内存中 jobs 列表随轮数增长到 ≤ ~140（每 20 轮主动 `clear_finished`），
  history 受代码上限约束在 40 条——这是现有产品行为（任务页保留本次会话任务，用户可
  手动清理），不是泄漏；soak 内主动清理也验证了该路径可用。

边界：这是"同一进程内连续 512 轮重复场景 + 指标趋势"，不是真实用户长时间负载。只在
采样点观察 RSS/FD/子进程/临时文件；**没有**宣称"已证明不存在任何泄漏"，只能说本轮
未观察到增长，也未发现跨轮累积。

### UI 列表渲染（`build/benchmark-ui-20261027-001830.json`）

用真实 headless Chrome 加载当前源码构建的页面，打开 1000 条 ZIP（后端返回 800 条）。
下表是本轮实际复跑的结果（单次）：

| 阶段 | 结果 |
| --- | --- |
| 初始 200 行（含 `/api/inspect` 往返） | 45.9 ms |
| 点「显示全部」→ 800 行（layout + 两帧后的 paint） | 111.7 ms，6,400 个节点 |

低于 300 ms 交互预算，B4 判定不变。之前的 155.7 / 245.7 ms 是更早轮次的数据，
不再作为本轮结论引用。

### B4 判定（不改造，保留现状）

现有实现首屏固定渲染 200 行；800 行只在用户主动点「显示全部」时一次性渲染。
本轮实测 111.7 ms，低于仓库交互反馈预算（DESIGN.md §4：交互 ≤ 300 ms），且不发生在
默认浏览路径上。**因此本轮不引入分页/虚拟滚动**：收益未被数据证明，而改造会直接
触碰 A1 的选中状态、焦点保持与现有 `extract_list_test`/`menu_test` 断言。

后续触发条件（满足任一条再重做基准并考虑改造）：

1. 同机同命令 `expand_to_800` 的 `painted_ms` > 300 ms 连续两次；
2. 后端列表上限从 800 提高（例如 2,000+ 条），或首屏行数提高到 400+；
3. 真机/低配机走查出现可感知滚动卡顿，或 A1 的勾选操作在展开后出现掉帧。
